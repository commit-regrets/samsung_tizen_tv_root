## Persistence store — `--global` writes the parser DB (2026-10-29 17:12 CET)

Compared with Vetro (`app/service/debloat.js` verifies
`package_app_info.app_disable` via `pkgcmd -D --global`; the owner override
it also reads is `package_app_info_for_uid.is_disabled`) and with
tizen-tv-control-center (`docs/03-debloat.md` checks the same column, and
tells you not to pass `--global` because it prints "Failed to get appinfo").

On this set, as root:

| call | callback | `app_disable` afterwards |
|---|---|---|
| `pkgcmd -D -t app -n <id>` | end ok | stays `false` |
| `pkgcmd -D -t app -n <id> --uid 5001` | end ok | stays `false` |
| `pkgcmd -D -t app -n <id> --global` | end ok | **`true`**, DB mtime moves |

All 11 tier-1 ids took the third form (exit 0, row `true`). A second
`--global` on an already-disabled id exits 25 with `Failed to get appinfo`
and leaves the row `true`. That is the message tcc treated as "do not use
`--global`". `pkgcmd -A --global` sets the row back to `false` (round-trip
on `adplatform.ADPlayer`, then disabled again).

`app_support_disable` is `false` for every package on this TV (count 0).
The per-uid table is empty in both the system DB and
`/opt/dbspace/user/5001/.pkgmgr_parser.db` (that file's mtime is still
2025-09-07). Vetro's owner-override table is unused here; the global column
is the one the launcher reads.

Tight window (`touch` ref, `--global` enable+disable of one id, `find
-newer`): the only persistent files written were

- `/opt/dbspace/.pkgmgr_parser.db`
- `/opt/dbspace/.pkgmgr_parser.db-journal`

Also touched, and wiped at boot because they are on tmpfs: `/run/aul/dbspace/.amd.db`
and `/run/buxton2/memory.db`. Not touched: persistent buxton
(`/opt/var/lib/buxton2`), `/mnt/systemrw`, the user parser DB, and the
root filesystem (`find / -xdev` was empty). An earlier wider window also
saw securestorage and sidebar sqlite change; the tight window shows those
were ordinary TV writes, not pkgcmd.

Launcher, uid 0: a disabled id returns exit 255, "not available for the
user 0". An enabled sibling (`com.samsung.tv.adagent-service`,
`org.tizen.pisa-control-service`) returns "result: not running". `org.tizen.menu`
and MultiControl-Service still report running. So the row is honored.

systemd does not honor it when `ExecStart` is the binary.
`systemctl start canalysis-service` ran `canalysis-daemon` while the row
was already `true`. The vendor unit has the persistent off switch:

```
ConditionPathExists=!/opt/usr/share/systemd/system/canalysis-daemon
```

An empty file at that path makes `systemctl start` report "start condition
failed" and leaves the process down. `pisa-service.service` and
`adagent-service.service` share `ConditionPathExists=!/opt/usr/share/systemd/system/pisa-service`
(the adagent unit is pisa's second binary, not `coba.adagent`). Both files
are on `/opt`. `/etc` is read-only, so `systemctl mask` cannot persist.
`/opt/usr/share/systemd/system/*.service.d` drop-ins are not loaded
(`systemctl cat` does not show them).

Units for the 11:

| app | how it starts | what keeps it down across boot, if the row survives |
|---|---|---|
| canalysis-service | direct binary, Restart=always | sentinel `canalysis-daemon` (planted) |
| pisa-service | direct binary | sentinel `pisa-service` (planted; also blocks adagent-service) |
| cis-api-service-app | `app_launcher -s`, Restart=on-failure/90s | the row makes the launch exit 255; the unit will retry every 90s. No sentinel in the unit, and `/etc` cannot take a mask |
| content-grab-service | `app_launcher -f`, only if a `/run` file exists | the row; no Restart= |
| the other 7 | no systemd unit (launchpad) | the row |

Undo on the TV: `/opt/usr/home/owner/share/debloat-undo-global-20261029.sh`
(`pkgcmd -A --global` for the 11, then `rm` of the two sentinel files).

**Not yet proven:** that `app_disable='true'` and the two sentinel files
are still there after a mains cycle, and that the process table stays down.
The parser DB is rewritten or checkpointed at boot (mtime jumped to boot
time on the previous cycle, when every row was still `false`). If that
pass rebuilds rows from manifests, the flags die and the fallback is the
boot payload re-asserting `--global` plus the two sentinel files. Do not
`systemctl --force reboot` from the payload. Owner pulls power; then
re-read the 11 flags, the two sentinel files, and `/proc/*/exe`.


## Cold-boot persistence test — PASSED (2026-10-29 17:51 UTC)

Owner mains-cycled the TV. Fresh boot, payload rooted, channel at uid 0.
Readback:

- **All 11 `app_disable=true` rows survived** in
  `/opt/dbspace/.pkgmgr_parser.db` — the `--global` store is persistent.
- **Both sentinel files survived** (`/opt/usr/share/systemd/system/
  canalysis-daemon`, `pisa-service`, dated pre-reboot) — canalysis,
  pisa and adagent units inactive after boot.
- **Zero tracking processes running** — the entire ACR/ad stack stayed down
  through the cold boot. `cis-api-service-app.service` inactive this boot
  (its 90 s retry never fired or gave up). `pisa-service.path` still active
  (harmless: the service it triggers is sentinel-blocked).

**Conclusion: tier 1 is durable with zero payload changes.** The disable
store (parser DB via `--global`) plus the two sentinel files on /opt are the
complete persistence mechanism; v42 boot re-assert is NOT needed for tier 1.
The same technique (pkgcmd -D --global + ConditionPathExists sentinels) is
the proven pattern for any future tier.

Remaining known state: `cis-api-service-app` may churn on 90 s retries if
its path trigger fires (no sentinel possible in its unit — watch it); the
`targeted-ad` overlay from the session is gone (one-shot) but unnecessary
(the row is true; the launcher refuses it).
